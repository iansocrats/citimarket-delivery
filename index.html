Domain 1: Fintech & Escrow Event Sourcing & CQRS

Why CRDTs Cannot Be Used for Money

CRDTs allow concurrent offline writes without coordination. If a customer has KSh 3,850 in their wallet and opens the app on two phones simultaneously while offline, a pure CRDT would allow them to spend that KSh 3,850 twice!

⚡ The Event Sourcing Solution:

All financial accounts are strictly linearized by a single central sequencer. Account balances are never directly updated; they are computed by folding over an immutable append-only ledger log where $\sum \text{Debits} \equiv \sum \text{Credits}$ ($\Delta = 0.00$).

Domain 2: Mobile Edge Devices CRDTs (Join-Semilattices)

Zero-Coordination Offline Mathematical Convergence

In Nairobi traffic and concrete buildings, couriers cannot wait for server handshakes. CRDTs use commutative merge functions ($A \sqcup B = B \sqcup A$) guaranteeing that no matter the order network packets arrive, all devices converge to the exact same state.

⚡ Production Use in CitiMarket:

• LWW-Register: Courier GPS coordinates merged without row locks.
• PN-Counters: Courier trip counts and fuel vouchers calculated offline.
• OR-Sets: Multi-tablet florist stem preparation checklists.

Zero-Knowledge Verification Salted Hash on Edge

Solving the "Basement Handover" Without Exposing the PIN

If the server sends the plaintext PIN (`8842`) to the courier's phone, a dishonest driver could read it and steal the flowers. If the server doesn't send anything, the driver can't verify delivery in an underground parking garage with zero 4G reception.

⚡ The Cryptographic Salt Protocol:

The cloud sends only a salted hash: $H = \text{SHA256}(\text{PIN} + \text{OrderID} + \text{Salt})$. The phone verifies the spoken PIN locally with 0ms server latency, generates an ECDSA signed proof token, and writes to SQLite outbox.
